# 发布与交付

先读取项目发布文档、实际 Git 根与工作区状态，明确目标环境、发布范围、运行基线和已有授权。分别判断提交、推送、部署是否已授权；所有产物（设计、用例、代码、缺陷和报告）未经本次人工批准不得提交，包括 WIP/checkpoint，除非用户明确批准范围内的自动提交。历史批准不覆盖新一轮变更，最终人工验收也不自动授权 Git。

从完整需求交付进入时，核对主 agent Review、独立测试报告及用户验收状态，不能把开发自测当成独立验收；若任务是为测试准备已授权的本地/测试部署，注明“待测试”并执行必要部署，不把最终验收错误地设为部署前提。生产部署按用户实际授权及项目发布条件执行。

## 准备可审阅的发布内容

1. 列出本次文件和变更，识别已有无关改动及嵌套仓库。按白名单处理，不使用全量暂存掺入无关文件，不覆盖用户改动。
2. 对照目标环境实际运行版本。只发布 hotfix 时从真实基线构建最小补丁，不能默认发布包含无关变化的主分支。
3. 核对数据库结构、迁移顺序、配置、依赖和制品之间的兼容性。迁移需隔离演练和对账，生产备份及恢复方法纳入发布准备；历史数据修复不随代码改动自动执行。
4. 执行与改动相称的测试，明确浏览器、真实数据库和外部依赖的验证边界。报告必须对应实际源码、配置及制品；未提交代码用 HEAD＋差异和相关文件哈希（含未跟踪文件）定位，不为记录版本自动创建提交。
5. 形成发布清单：目标环境、基线、变更、制品标识、命令、配置/迁移顺序、验收项、回退条件和恢复步骤。缺少授权时先完成这些可审阅准备，再询问具体待执行动作。

## 执行与验收

- 已授权的提交前检查 staged 文件与 diff；只处理白名单。推送后比对本地提交与远端目标分支 SHA。
- 按项目既有流程发布；核对实际加载的 JAR、镜像或静态资源，不能仅凭构建成功判断已部署。
- 验证容器健康、日志、实际入口和关键业务链路；涉及代理、认证、异步处理或持久化时验证到对应终点。
- DATETIME + LocalDateTime 服务变更时区时，检查应用真实连接池 session，不以人工连接结果替代；验证数据库和 Java 时间一致。
- 发布失败或验收异常时暂停继续扩散。按已授权且适用的回退方案恢复；涉及不可逆数据恢复或范围外操作时交付现状并取得明确授权，禁止盲目重复发布。

## 输出与完成标准

报告目标环境、实际版本/提交/制品、变更范围、迁移状态、验收证据及未完成项。将“准备完成、已提交、已推送、已部署、已验收”分开描述，不跳级宣称完成。回退代码并不自动回退数据库，必须说明实际兼容性和数据恢复状态。
