# 证据驱动根因排查

先明确故障环境、复现条件与授权。只读排查不修改代码、配置、数据或部署；已有修复授权则在确认原因后完成必要修复与验证。

## 工作流程

1. 保存原始症状和最小复现：请求入口、时间、身份、traceId、结果；保护缓存及用户要求保留的现场。
2. 建立少量可区分的假设，列出支持证据、反证、下一项最小验证。不要反复重试同一失败操作代替调查。
3. 按故障路径定位：请求/身份 → 权限 → 业务与数据 → 配置/制品 → 网络代理 → 页面表现。只检查相关层级。
4. 比较最近正常与失败条件，包括代码版本、依赖、环境变量、数据库结构/数据、缓存、部署产物和入口变化。正常基线不可得时明确无法证明触发变化。
5. 检查运行实例实际加载的内容：源代码已改不代表 JAR、静态资源或容器已更新；服务内部成功不代表公网 DNS、TLS、Host 或代理链路成功。
6. 将“变化 → 触发条件 → 代码或配置行为 → 故障结果”连成证据链。区分直接原因、触发变化与扩大影响的条件。
7. 提出最小修复及验证方式；授权修复后验证原始复现和受影响路径。不要以静默降级掩盖未解决的故障。

## 输出

- 结论与可信范围。
- 根因及证据位置。
- 以前正常的条件及触发变化；未证实的部分标记未知。
- 修复建议或实际改动。
- 验证结果、剩余风险和未完成项。

## 完成标准

证据能够解释观察到的现象，并排除主要竞争假设；不能确定根因时交付已排除项和下一项明确验证，不编造确定结论。
