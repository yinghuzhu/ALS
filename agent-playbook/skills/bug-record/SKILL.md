# 缺陷记录

读取目标项目现有缺陷格式和编号规则，搜索同一问题，优先补充已有记录。用户指定跨项目归属时使用指定目录；无法确定归属则标记待确认，不擅自指派他人。

## 路径与编号

- 先定位目标项目根及既有文档根约定；本技能中的 `docs/bugs/` 相对该目标项目解析，不相对 skill 安装目录，也不假定调用时工作目录就是项目根。
- 既有明确命名约定优先。无约定时新增文件用 `docs/bugs/BUG-YYYYMMDD-NNN-<bug-slug>.md`，例如 `docs/bugs/BUG-20261030-001-approval-group-resolution.md`。稳定 ID 为 `BUG-YYYYMMDD-NNN`；`bug-slug` 用简短、有意义的小写英文 kebab-case 描述现象或受影响行为，不用 `bug1`、`fix` 等模糊后缀。
- 日期为首次记录日期。分配当日 `NNN` 前，检查该日全部已有记录，包括 `BUG-YYYYMMDD-NNN.md` 旧式文件；后缀不同不能重复分配同一 ID。同一问题补充或复验时沿用原记录，不因新日期重复建档。
- 不自动批量重命名历史文件。用户明确要求改名时保留稳定 ID 并同步引用和索引；同一 ID 继续追溯同一问题。
- Skill 内部相对资源按包含引用的文件所在目录解析；安装和工具目录在运行时发现或由参数/环境提供，通用模板不绑定开发机用户名、仓库及临时目录的绝对路径。系统约定路径、API 路径和运行时合法路径不受此限制。

## 工作流程

1. 提取环境、版本、入口、身份/权限、前置数据、操作和错误表现。只记录验证过的事实；无法复现的标明来源和状态。
2. 将预期行为与实际行为分开。记录日志、请求、代码位置或数据库结果的最小证据，脱敏凭据与个人数据。
3. 分开写根因证据、待验证假设、建议修复、已批准方案；不要把建议描述成已实施。
4. 写清影响范围与回归条件，包括受影响旧路径、隔离边界和兼容要求。
5. 保存记录并反馈位置。用户只要求记录时到此完成；向飞书等外部平台创建任务或发送消息需要明确授权，已给出的授权不重复索取。

## 开发与测试闭环中的问题状态

- 测试 agent 提供用例编号、确认预期、实际结果、复现及版本证据；普通问题一轮后汇总，阻断或污染问题立即报告。测试者不修业务代码或修改预期来使问题消失。
- 开发确认原因并可提供反证；主 agent 对照已确认设计判断明确偏差，不能允许开发单方面否决测试证据。环境/夹具错误单独记录并重测；无法复现保留条件和证据，不自动关闭。
- 业务规则冲突、需决策的设计遗漏或新增需求进入“待裁决”，由用户决定，主 agent 同步设计及用例。明确缺陷在已授权范围内自主修复，不必每轮向用户申请。
- 默认状态：待确认 → 已确认／待裁决 → 修复中 → 待复验 → 已关闭。开发修复完成只能进入待复验；主 agent Review 后，由不同于开发者的测试 agent 复验原失败与关联回归，主 agent 核验证据再关闭。复验失败返回已确认或修复中，保留历史轮次。
- 判定非缺陷需主 agent 记录确认契约与反证；存在业务争议则由用户裁决。延期或不修需用户批准，标为已裁决延期等独立状态，不能改成通过或冒充修复关闭。
- 状态变化记录处理者、待测/修复版本及证据。用户只授权记录时不推进修复；任何缺陷文档或报告未经本次批准也不得提交 Git。

## 默认模板

文件按上述路径与编号规则命名，正文标题保留稳定 ID 与可读问题标题：

```markdown
# BUG-YYYYMMDD-NNN 问题标题
- 状态：待确认 / 已确认 / 待裁决 / 修复中 / 待复验 / 已关闭 / 已裁决延期
- 严重程度及理由：
- 所属模块：
- 环境、源码/制品与设计/用例版本：
- 关联用例编号与发现轮次：

## 现象与复现
前置条件、操作步骤、预期、实际、复现稳定性。
## 证据
脱敏后的日志/请求/数据与代码位置。
## 原因与变化
已确认根因；历史正常条件；触发变化；未知项。
## 影响与方案
影响范围、建议方案、批准状态、兼容与风险。
## 验收条件
可重复验证的通过标准及回归范围。
## 处理记录
每轮确认/裁决、开发修复、主 agent Review、测试复验、主 agent 核验记录，包含处理者、版本及证据；未发生的动作不填写为完成。
```

## 完成标准

别人能够依据记录理解并复现或继续调查；未知信息显式保留；没有因创建记录而虚报修复、发布或关闭。
