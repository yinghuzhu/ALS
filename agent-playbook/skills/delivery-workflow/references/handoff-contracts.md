# 交接契约

用于主 agent 编写或检查阶段交付。完整需求交付优先填入项目已有文档；没有既有结构时，至少提供详细设计和唯一权威测试用例两份文档，命令/环境说明及执行结果分别存放。实施计划、角色任务单和处理记录可作为现有文档的章节，不要求额外拆文件。只记 bug、只读检查或其他单阶段任务只产出当前范围所需内容，不强加完整需求文档。

## 路径与默认目录

Skill 内部引用以包含引用的文件所在目录为基准，例如本文件回到入口可用 [SKILL.md](../SKILL.md)；不以调用时工作目录或原始源码仓库为基准。安装/工具位置在运行时发现，或由参数/环境提供，模板不绑定本机用户名、仓库和临时目录的绝对路径。

项目产物的 `docs/` 相对执行时定位的目标项目根解析，或按项目已有文档根约定解析，不放到 skill 安装目录。既有明确命名约定优先；完整需求没有既有约定时默认：

```text
docs/requirements/YYYY-MM-DD-<requirement-slug>/
├── design.md
└── test-cases.md
```

例如 `docs/requirements/2026-10-30-approval-routing-policy/`。日期为首次建档日期，修订不改日期；`requirement-slug` 用简短、有意义的小写英文 kebab-case 描述需求，避免 `feature1`、`fix` 等模糊名称。`implementation-plan.md`、`ddl.sql`、`runbook.md` 等只在确有内容需要时增加。

新规则不触发历史目录批量重命名。用户明确要求改名时保留首次建档日期、已有需求标识，并同步引用和索引。这里只规定完整需求交付的默认目录，不给单阶段任务增加交付物。

## 设计与用例

### 详细设计的最小内容

| 内容 | 可交付标准 |
| --- | --- |
| 需求与边界 | 需求编号、目标、非目标、验收条件、已裁决规则；待决策项不得伪装成确定结论 |
| 现状与证据 | 仓库/分支/提交、相关工作区变更、代码入口、表结构/DDL 和配置来源；明确未核验的数据库或运行环境 |
| 新项目情况 | 明确无现有实现；给出技术选型、模块边界、目录、外部契约与运行前提；不虚构旧接口和迁移要求 |
| 实施差异 | 每项列当前行为、证据、复用/修改/新增、具体差异、调用方/兼容影响及用例编号 |
| 行为契约 | 正常/边界/失败行为、状态流转、权限、接口输入输出和错误语义；复杂流程用可读流程图/时序图/状态图辅助 |
| 数据与运行 | 涉及的数据结构、约束、事务、一致性、配置、迁移/部署顺序及回退；不涉及项标明不适用及理由 |
| 确认基线 | 设计与用例共同的版本标识、用户确认的范围及实施授权；变更记录链接到新裁决 |

实施项表可直接使用：

| 需求/实施项 | 当前行为与证据 | 复用/修改/新增 | 修改范围与规则差异 | 受影响调用方/兼容 | 验证用例 |
| --- | --- | --- | --- | --- | --- |
| 填写实际需求 | 文件、类/方法、表/配置与已核验行为 | 选择一项 | 具体到执行者无需决定业务语义 | 具体依赖及保护条件 | 用例路径＋编号 |

不能把上述占位行当作已完成计划；新增项还要记录检索范围和不能复用的原因。

### 唯一权威测试用例

每条用例提供：稳定编号、需求/规则关联、适用版本、角色与权限、前置状态和数据、逐步操作、每步可判定预期、数据核对与清理条件。精确到实际输入、页面入口/API 行为和可观察输出；环境 ID 可以引用运行说明中已提供的具体清单，不写入真实凭据。

既有用例按原路径＋编号引用，保持追溯关系。覆盖映射列出复用、修改、新增或废弃及原因；必跑清单包含受影响旧功能。不同测试层级的有效覆盖可以保留，不能只因描述相似删除。

命令、环境启动、账号获取、固定数据准备与恢复放运行说明；每轮执行结果放报告。没有可执行的前置方案、权限或数据时，明确缺口和负责人。用例不能用“按部署方案处理”引用尚不存在的文件，也不能把“检查正常”当作预期。

## 派工模型与上下文记录

开发和测试任务单均记录：角色、所选模型、选择理由；发生升级时补充原模型、失败或能力不足的证据及调整原因。实际模型不可核实时明确标记，不用请求参数冒充运行确认或实际费用。

新 agent 未继承会话时，任务单显式附上适用规则、确认设计与用例的可读取路径和版本、代码基线、已有结果、授权边界及回传要求。升级时继续保留这些交接信息和角色隔离，不重启已完成的整套流程。

## 开发任务单与回传

主 agent 下达任务时提供：

- 确认后的设计/用例路径与版本、用户实施授权范围。
- 仓库、基线及已有改动；允许修改的文件/模块、保护边界和禁止动作。
- 本轮需求或缺陷编号、必须保留的兼容行为、预期交付与测试范围。
- 依赖和阻塞条件；业务歧义回传主 agent，不自行补规则。
- 明确无本次批准不得提交任何产物，也不得因工具要求自动提交。

开发回传：需求/缺陷到变更的对应表、实际文件差异、单元测试/自测结果及证据、未测项与已知问题、可复核的待审版本。单元测试 Mock 外部服务，真实数据库和外部链路验证另列；不能宣称自测替代独立验收。

## 主 agent Review 记录

记录受审版本及范围，并检查实际代码而不是只读开发总结。问题至少包括编号、位置、与已确认设计的偏差或可复现风险、影响、修正目标及验证条件。检查遗漏功能、重复实现、共享调用方、权限/事务/兼容、失败行为、测试断言及文档。

每条问题保留开发处理说明和主 agent 复查证据。未修复的明确问题不能仅凭开发标记完成而通过；若属于范围外建议，明确不作为当前阻断项，不能擅自扩展需求。

## 测试任务单与回传

主 agent 交接给不同于开发者的测试 agent：

- 已确认设计/用例版本、Review 通过的范围、必跑用例路径＋编号。
- 待测源码和实际制品标识，环境入口、权限/数据清单、允许的夹具操作及恢复方法。
- 环境独占/隔离安排；禁止修改业务代码、改变预期或降低断言、提交 Git、发布生产。
- 本轮目的：首次测试或指定缺陷复验＋受影响回归；已知阻塞和问题回传位置。

每轮报告至少包含：轮次、执行者、设计/用例版本、待测源码/制品、时间、每条用例的 PASS/FAIL/BLOCKED/NOT_RUN、实际观察与证据、缺陷编号、恢复结果和待办。

未提交版本记录 HEAD＋差异和相关文件哈希，覆盖未跟踪文件；无 Git 基线的新项目使用文件清单与哈希。后续源码、配置、数据前提或产物变化时由主 agent 评估影响并安排必要复验，不能用旧结果证明新版本通过。测试 agent 不自行切换产物或接收开发边改边测而不更新记录。

普通缺陷完成一轮后汇总；阻断或污染立即上报。对没有受影响的场景继续执行；无法执行的具体用例标记阻塞并说明依赖，不以“环境问题”一笔抹去。

## 问题确认与关闭

| 分类 | 处理责任与证据 |
| --- | --- |
| 明确违反已确认设计 | 开发调查修复；主 agent Review；测试复验；主 agent 核验关闭 |
| 环境/夹具问题 | 保留失败记录，在授权范围修正环境/数据后重测；不直接标业务通过 |
| 用例与确认设计冲突 | 主 agent 核对确认记录，修订有证据的错误；改变业务预期须用户裁决 |
| 设计遗漏、规则矛盾、新需求 | 主 agent 向用户呈现事实、选择与影响，待裁决后同步设计和用例 |
| 无法复现 | 保留原证据、复现条件与排查结果；不因一次未复现直接关闭 |

默认状态为“待确认 → 已确认/待裁决 → 修复中 → 待复验 → 已关闭”。环境问题可记录“待环境修复”；用户批准延期则标“已裁决延期”，不能计为通过。复验失败回到已确认或修复中，保留历史轮次。

开发只能提交修复说明与自测证据，不能自行关闭。关闭需测试 agent 对原失败和关联回归的结果、主 agent 核验记录；判定非缺陷需主 agent 给出已确认契约和反证，存在业务争议则交用户裁决。

## 最终人工验收包

交付同版设计/用例、最终变更清单、主 agent Review 结论、测试报告、缺陷状态及用户已裁决例外，提供实际验收入口。主 agent 说明“待人工验收”，不替用户宣布验收通过。

用户验收通过后，仍须核对本次 Git 批准的文件与动作范围；设计、用例和报告也受同样约束。没有 Git 批准就保留工作区，不能为了归档、角色交接或快照创建提交。推送、部署和生产验收按各自实际授权与证据报告。
