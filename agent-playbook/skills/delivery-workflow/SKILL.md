# 需求交付流程

先读取项目规则、当前任务、已有设计与用例及确认记录，定位实际阶段。复用已确认内容，不重新启动整个流程。用户明确缩小范围时只完成该范围。

## 资源路径与产物位置

公开的说明、示例、报告及链接目标同样不得包含真实用户名或本机目录；展示时保留项目相对路径或使用 `<skill-dir>`、`<project-root>` 占位符，不把运行时解析出的绝对路径复制到对外内容。

本 skill 内部资源用相对引用，按包含该引用的文件所在目录解析；下文 `references/handoff-contracts.md` 相对本 SKILL.md 所在目录，不依赖调用时工作目录或原始仓库路径。安装目录和工具目录须运行时发现，或由参数/环境提供，不写开发机用户名、仓库或临时目录绝对路径；此限制不适用于系统约定路径、API 路径及运行时核验得到的合法路径。

项目产物路径以执行时定位的目标项目根为基准，或遵循其既有文档根约定，不相对 skill 安装目录。完整需求交付无既有命名约定时使用 `docs/requirements/YYYY-MM-DD-<requirement-slug>/`；日期为首次建档日期，后缀为简短、有意义的小写英文 kebab-case，修订不改日期。目录内提供 `design.md`、`test-cases.md`，实施计划、DDL、运行说明按需，不要求只读或单阶段任务创建完整文档。既有明确约定优先，不自动批量改名历史目录；用户要求改名时保留首次日期并同步引用和索引。

## 角色与权限

- 用户与主 agent 共同完成需求、详细设计和测试用例，用户裁决业务歧义、最终验收并批准 Git。
- 主 agent 负责分配、推进、亲自 Review 实际变更、核验证据；Review 辅助工具不能替代主 agent 的结论。
- 开发 agent 负责实现、单元测试、自测、明确缺陷修复。另一测试 agent 负责独立执行确认用例、记录实际结果与问题，不改业务代码或预期来获得通过。
- 角色交接使用可用的 agent 工具；不因技能存在而授权向真实人员发送外部消息。工具无法提供独立执行者时说明限制，等待用户接受分工降级，不能将开发自测冒充独立测试。
- 所有产物未经本次人工批准不得 commit，包括设计、用例、报告及 WIP/checkpoint；已批准的范围不重复询问，历史批准不覆盖新增变更。最终验收、提交、推送、部署分别核对授权。

## 派工时的执行方式与模型选择

首次派工前读取 [执行者配置与默认发现名单](references/agent-selection.md)，读取本 skill 的 [agents.yaml](agents.yaml) 作为默认配置，再按目标项目配置覆盖。用户可直接编辑该 YAML；候选以文件为准，不另维护写死名单。

1. 建立统一候选池：当前平台内置子 agent 可选模型与本地 CLI agent＋模型平等参与。核对能力、模型参数和上下文限制，优先满足任务要求且成本较低的组合；默认不沿用主 agent 的高成本型号，不硬编码型号或未经核验的价格。
2. CLI 按合并后的配置发现，支持增删候选或指定路径；仅检查配置中的命令名（可用 `command -v <命令>`）和用户指定路径，不扫描整机。读取已安装版本的帮助，确认模型参数、工作目录、任务输入、输出及权限控制方式；不能凭其他 CLI 的参数拼命令，不自动安装。无法执行所需任务或维持角色权限的候选标记不可用。
3. 区分“已安装／待运行验证／已验证／不可用”。可读取登录或模型配置状态，但不输出凭据；默认不额外发起模型探测，以首个已授权实际任务验证服务和模型权限。版本命令成功不代表服务正常；待运行验证项须明示不确定性，已知不可用项不作为可执行选择。本地 CLI 可能连接远程服务，列明已知服务商，未知则标记待核实。
4. 设计和用例确认且实施已授权后，首次开发派工前须已有开发与测试的有效选择或自动选择授权；从中间阶段接入时在该角色首次派工前完成。缺少选择时，按 [交接契约](references/handoff-contracts.md) 展示一张统一候选表，由用户分别确定开发、测试的首选及有序备用，或授权主 agent 在候选范围、预算内自动选择。备用可跨内置与 CLI；本需求内复用配置，不每轮询问，不静默超出已选范围。
5. 派工时记录执行方式、模型及理由，提供工作目录、确认设计与用例、基线、适用规则、允许动作及回传证据。内置模型覆盖若与完整历史继承互斥，使用独立上下文；CLI 同样显式交接，不能假定它自动加载 AGENTS.md 或 skill。开发和测试必须使用独立会话；同一种 CLI 或模型可分别承担两种角色，主 agent 仍亲自 Review。
6. 核验退出状态、实际文件差异、测试结果及证据，不能把进程启动或退出码为零当作完成。请求模型与实际可核实模型分别记录；未暴露的实际模型或费用标记未知。不能指定模型且无法满足用户明确限制时报告，不假装已按要求执行。

### 失败与切换

- 明确额度耗尽或模型无权限时直接选择下一备用；短暂网络、限流或服务故障默认最多重试一次，再按备用顺序切换，遵守服务提示的等待时间及任务预算。候选耗尽后报告阻塞，不循环回到已失败候选。
- 每次重试或切换前，确认旧执行已终止，核对已改文件、已执行的数据操作及结果；不能确定是否仍在运行或操作是否生效时，先查明状态，不启动可能重复写入的替代任务。保留已有工作，不盲目回滚或从头重放。
- 给新执行者交接已确认进度、未完成项和当前基线，维持角色隔离；待测版本变化时重新核定 Review 和回归范围。记录失败证据、原执行者、切换目标及原因，并向用户告知，已授权的备用无需逐次确认。
- 代码缺陷、断言失败、业务歧义和环境数据缺口不当作服务故障。正常修复仍遵守 Review／测试循环；能力不足先补上下文或拆任务，再在已授权范围升级。超出候选、供应商、预算或业务规则的决定交用户，不用换模型猜测。

## 阶段与交付

| 阶段 | 进入条件 | 执行者与交付物 | 退出条件 |
| --- | --- | --- | --- |
| 需求与现状核对 | 用户提出需求或变更 | 用户＋主 agent：需求范围、现状证据、待决策项 | 业务目标与边界清楚，未知项可见 |
| 详细设计与用例 | 已有明确范围 | 用户＋主 agent：同版详细设计、唯一权威用例；复用现有实施计划 | 业务歧义已裁决，设计和用例获人工确认，实施已授权 |
| 实现与自测 | 上一阶段通过 | 开发 agent：范围内变更、单元测试、自测结果、差异清单 | 需求逐项有实现对应，已知问题和未测项明确 |
| 代码 Review | 开发交接就绪 | 主 agent：基于实际 diff 的问题清单或通过结论 | 明确问题已由开发修复且主 agent 复查通过；否则回到实现 |
| 独立测试 | Review 通过，环境/数据/待测版本就绪 | 测试 agent：按必跑清单执行，输出逐项报告和缺陷 | 本轮完成或明确阻塞；问题交开发确认，不自动宣布最终验收 |
| 缺陷闭环 | 测试发现偏差 | 开发修复 → 主 agent Review → 测试复验 → 主 agent 核验 | 原失败及关联回归通过，问题有关闭证据；歧义先交用户裁决 |
| 人工验收 | 必跑项有实际结果，必修问题关闭，文档与代码一致 | 主 agent：验收入口、证据、已裁决例外；用户验收 | 用户确认验收，或反馈后回到对应阶段 |
| Git／发布交付 | 对应动作已有人工授权 | 按本次白名单和既有发布流程执行 | 报告实际完成的提交、推送或部署，不混同验收状态 |

## 设计阶段的必要检查

读取 [交接契约](references/handoff-contracts.md) 的“设计与用例”部分，补入项目现有文档，不强制新建一套重复文档。

存量项目逐项核对当前代码、调用链、表结构或 DDL 与配置，记录分支/提交、相关工作区差异和未核验环境。每项归为复用、修改、新增，新增须说明现有能力不能满足的原因。新项目明确没有现有实现，给出技术、模块、数据、接口、状态、异常、权限和运行约束，不能凭空填写代码证据。

设计与用例同版维护；旧用例按路径和编号复用，检查重复、冲突及受影响旧流程。前置方案必须真实存在并可执行；“按方案处理”“结果正常”不能替代明确步骤与可判定预期。尚缺账号、数据、外部契约或规则时列为缺口，不交执行者猜测。“无歧义”是消除未定业务规则、接口契约或架构取舍；不改变确认契约的常规实现细节由开发自行处理，不为变量命名等普通细节反复询问。

需求改变时，主 agent 更新设计、用例和影响范围；业务规则变化先与用户确认，只暂停依赖裁决的工作，继续无依赖部分。只重做受影响的实现、Review 和测试，不能沿用失效确认或无关地重跑全部流程。

## Review 与测试循环

- 派工时使用交接契约中的角色任务单，明确文件范围、确认版本、可执行动作和回传证据；同一工作区不得并行写同一文件，测试数据须独占或隔离。
- 主 agent Review 检查设计覆盖、复用与共享调用方、权限/事务/兼容、异常和数据一致性、测试断言及文档一致性。每条问题给出位置、证据、影响及验证条件；开发声称“已修复”不能替代复查。
- 每轮 QA 固定待测源码和实际产物。未提交时用 HEAD、完整差异与相关文件哈希（含未跟踪文件）、制品标识定位；新项目可用文件清单与哈希。不得为生成测试基线擅自 commit。
- 测试按已确认预期执行，普通问题完成一轮后汇总；阻断后续操作、污染数据或危及环境的故障立即报告，继续不依赖该故障的用例。环境问题与业务缺陷分开记录，不以环境不可测判定业务通过。
- 开发提供原因或反证，主 agent 判断是否违反已确认契约；业务冲突、设计遗漏导致的决策或新增需求交用户裁决。禁止开发单方否决证据、测试私改预期、主 agent 擅自扩大范围。明确缺陷的修复复测自主推进，无需每轮人工批准。
- 修复经主 agent 复查后，由测试 agent 复验原失败用例和关联回归。主 agent 核验结果再关闭；延期、不修或降低范围须有用户裁决，不能冒充通过。同一问题反复出现时重新调查原因，不机械重复同一修复。

## 结束与技能复用

完整交付达到自动验证条件后只能报告“待人工验收”，附最终版本、覆盖范围、缺陷状态和实际证据。未执行、阻塞或未裁决问题不得藏在“全部通过”中；用户批准的例外按例外报告。

按需要复用 `acceptance-qa`（用例与业务验收）、`bug-record`（问题状态与证据）、可用的 `review`／`investigate`（辅助检查与调查）、`release-delivery`（已授权部署）。仅在相应技能实际可读取时使用；缺失时按本流程完成当前可执行部分。独立测试角色可复用报告型 QA，不能启用 `qa` 的自动修复/提交来跨越角色边界。
