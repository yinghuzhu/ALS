# 共用工程协作约束

本文件是供目标项目合并使用的规则模板。本目录内编辑工作也遵守这些规则。业务约束按适用场景执行，不因项目未采用 MySQL、Java 或容器而引入这些技术。

## 工作范围与交付

- 默认中文输出，代码、API 和固定标签保留原文。
- “只分析、先讨论、不要改代码”限定为只读调查与讨论。记录缺陷不代表授权修复，发布本地不代表授权生产发布。
- 所有交付物（设计、用例、代码、缺陷及报告）未经本次人工批准不得提交 Git，包括 WIP、checkpoint 和工具自动提交；明确批准自动提交时仅按批准范围执行。历史提交授权不覆盖新一轮变更，人工验收通过也不自动授权提交。已明确授权的操作不重复询问；推送、部署与外部消息不得从其他动作推定授权。
- 修改前识别实际 Git 根及已有改动；只暂存本次授权文件，不覆盖或提交他人的改动。
- 排障必须用证据说明根本原因、以前正常的条件、触发失败的变化。无法证明的部分标记未知，不能用推测补齐。
- 交付说明写明改动、原因、验证及未完成项。构建成功、HTTP 200、容器健康、Mock 测试不能代替端到端验收。

## Git Tag 规则

- 发布 tag 统一采用 `YYYYMMDDNN`：8 位发布日期加 2 位当天发布序号，序号从 `01` 开始。例如 `2026102801` 为 2026 年 10 月 28 日第 1 批发布，`2026102802` 为当天第 2 批发布。
- 同一批发布涉及的所有服务仓库使用相同 tag 名称，各自固定到本次已确认、已验证的提交；发布记录列明服务、tag 和对应 commit SHA。
- 创建前核对本批涉及仓库的远程 tag，使用当天尚未占用的下一序号，避免把不同批次复用为同一发布编号。
- 发布使用带注释的 tag（annotated tag），推送至远程后，Jenkins 按该 tag 构建发布，不以持续变化的分支 HEAD 代替发布版本。
- 已推送的发布 tag 不得移动、覆盖或删除重建。后续修复必须使用新的发布序号；跨日期发布使用新日期并从 `01` 开始。
- 创建和推送发布 tag 须取得用户明确授权；确认命名规则本身不代表授权创建 tag 或触发发布。

## 需求交付分工与阶段

新需求默认按以下分工交付；单次只读调查、文档编辑或小范围修复按当前任务执行，不自动扩成完整生命周期。

- 用户与主 agent 共同讨论需求、形成详细设计和测试用例，可多轮沟通。详细设计与唯一权威用例必须属于同一确认版本；两者已获人工确认且实施已授权，才交开发 agent。已有确认不重复询问。
- 主 agent 负责推进、交接、亲自 Review 开发的实际变更、核验证据和汇报。不同 agent 分别承担开发和测试；开发负责实现、单元测试、自测及已确认缺陷修复，测试负责按确认用例执行、举证和记录问题。
- 设计必须让开发无需自行决定未定业务规则、接口契约或架构取舍；不改变确认契约的常规实现细节由开发自行处理，不逐项申请批准。用例必须让测试无需猜测操作与预期。不能用“按方案处理”引用不存在的方案，也不能以“结果正常”作为通过标准。缺口在开发前补齐；新业务歧义由用户裁决，只暂停依赖该裁决的工作，可继续无依赖部分。
- 开发完成后先交主 agent Review。明确问题交开发修复，主 agent 复查通过后再交测试；Review 与修复可多轮自主进行，不用每轮向用户申请确认。
- 测试 agent 不修改业务代码、不改变业务预期或降低断言以获得通过；开发自测不替代独立测试。没有可用独立 agent 时报告限制，只有用户接受降级后才能变更分工，不得冒充独立测试已完成。
- 每轮测试固定代码和实际制品版本；未提交时用 HEAD、差异、包含未跟踪文件的文件哈希或制品标识定位，禁止为固定版本擅自提交。环境与测试数据独占或隔离，版本变化后重新核定受影响 Review 和回归范围。
- 普通问题在一轮测试后汇总交开发确认；阻断后续测试或污染数据的问题立即报告，继续可独立执行的用例。开发可提供反证，不得单方面否决测试证据；主 agent 判断明确偏差，业务冲突或新增需求交用户裁决。
- 修复闭环为“开发修复 → 主 agent 复查 → 测试复验原失败及关联回归 → 主 agent 核验关闭”。开发不能自行关闭问题；延期或不修须有用户裁决，不能改标通过。保留每轮问题、版本及验证证据。
- 需求、代码、设计和用例一致，必跑项均有实际结果且必须修复的问题已复验关闭后，主 agent 交付待人工验收。用户负责最终验收及 Git 批准；中间明确缺陷的 Review／修复／测试循环由团队自主完成。

## 子 agent 模型选择

- 主 agent 派发开发、测试任务时，核对平台实际可选模型及工具限制，优先选择足以完成任务且成本较低的模型，默认不沿用主 agent 的高成本模型；不固定绑定具体型号。开发与测试分别选择，模型选择不改变角色独立性。
- 明确设计下的常规实现、单测、缺陷修复和按用例执行优先使用低成本模型；复杂跨模块分析或连续失败时，由主 agent 先检查任务、上下文和环境，再决定拆分或升级，必要时可使用主 agent 同款模型。不得为节省成本降低 Review、测试覆盖和证据要求，也不得反复盲目重试。
- 在现有任务单或交接记录中简述所选模型、选择理由及升级原因；工具未暴露实际模型时标记未核实，不声称已降低费用。无法指定模型时说明限制，继续按现有授权和分工执行；用户明确设定的预算或模型限制无法满足时，先报告再执行依赖部分。
- 指定模型导致不能继承完整会话时，显式提供确认设计与用例版本、代码基线、相关规则、授权边界、任务范围及交付证据，不假定子 agent 已知对话历史。用户明确指定模型时优先遵从。

## 路径与文档命名

- Skill 内部资源使用相对路径，按包含该引用的文件所在目录解析，不依赖调用时工作目录或原始源码仓库位置。项目 `docs/` 等产物路径相对执行时定位的目标项目根，或遵循该项目已有文档根约定，不相对 skill 安装目录。
- Skill 安装目录、工具目录在运行时发现，或由参数/环境变量提供；通用规则和模板不写开发机用户名、仓库或临时目录的绝对路径。这不禁止系统约定路径、API 路径及运行时核验得到的合法路径。
- 既有明确命名约定优先。无既有约定时，新增缺陷文件用 `docs/bugs/BUG-YYYYMMDD-NNN-<bug-slug>.md`，稳定 ID 为 `BUG-YYYYMMDD-NNN`，描述性后缀使用简短、有意义的小写英文 kebab-case。分配编号须核对当日所有已有记录，包括旧式无后缀文件；同一问题沿用记录，不因日期或后缀变化重复建档。
- 完整需求交付默认目录为 `docs/requirements/YYYY-MM-DD-<requirement-slug>/`，日期为首次建档日期；内含 `design.md`、`test-cases.md`，实施计划、DDL 和运行说明按需补充。该要求不扩展只记 bug、只读检查或单阶段任务的范围。
- 不为应用新模板批量重命名历史记录；用户明确要求改名时保留稳定 ID 或首次建档日期，并同步引用和索引，保持追溯关系。

## 技能选择与组合

按当前任务目标和交付物选择 skill，不按“测试人员、开发人员”等角色或单个关键词机械匹配。用户明确指定技能时优先使用；否则按下表选择，每个阶段只设一个主 skill，避免重复运行相同流程。

| 任务目标 | 主 skill | 适用边界 |
| --- | --- | --- |
| 主 agent 推进新需求从讨论、设计到开发、Review、独立测试和人工验收 | `delivery-workflow` | 编排阶段与角色交接，按已有确认从当前阶段接入；不替代具体开发、Review 或 QA 能力 |
| 浏览器探索、检查网站并报告问题 | `qa-only` | 只检查和报告，不修复 |
| 浏览器测试，发现问题后修复并复测 | `qa` | 仅在任务明确允许同一执行者测试及修复时使用；独立测试 agent 不启用其自动修复步骤，提交仍受人工确认约束 |
| 验证完整业务流程、金额数量、页面/接口/数据库及关联汇总一致性，交接人工验收 | `acceptance-qa` | 以业务预期和数据对账为核心；需要浏览器探索时可复用 QA 能力，不重复整套流程 |
| 将问题记录到项目 bugs 目录或整理跨项目缺陷交接 | `bug-record` | 沿用现有格式和编号；记录不等于修复、外部发送或关闭 |
| 查找报错根因、解释以前正常及失败触发变化 | `investigate` | 默认排障入口；遵守只读范围及运行制品、版本变化的证据要求 |
| 准备提交、推送和创建 PR | `ship` | Git/PR 交付，按本次授权选择步骤，不默认授权部署 |
| 合并 PR、等待 CI 部署并验证上线 | `land-and-deploy` | 适用于以 PR 和 CI 驱动的部署，须覆盖相应操作授权 |
| 部署本地/测试/生产服务器的 Docker、JAR，或基于生产版本发布窄范围 hotfix | `release-delivery` | 自托管发布，核对实际制品、配置、迁移、验收与回退 |

### 可用性与名称

- 使用前检查当前会话技能目录，并读取所选 SKILL.md；不能只凭名称猜测技能内容或假定已安装。
- 表中名称使用当前版本：`acceptance-qa` 和 `release-delivery`。`business-acceptance`、`self-hosted-release` 是曾讨论的候选名称，未实际完成改名和同步前不要作为入口调用。
- `root-cause-investigation` 当前仍是独立草案，与 `investigate` 重叠。默认使用 `investigate`；用户明确指定该草案，或 `investigate` 不可用且该草案可读取时，才使用它，不连续运行两套排障流程。
- 同步本 AGENTS.md 不等于安装 skill。技能未安装但用户提供了可读取的 SKILL.md 路径时，可按该文件执行；找不到时明确说明，使用可用能力完成已授权工作，不声称已调用该技能。缺失技能是用户明确要求且不可替代的前提时，说明阻塞原因。
- 不自动安装、覆盖或修改全局技能；实际改名或合并后同步更新本表，避免保留失效入口。

### 组合与授权

- 完整新需求由 `delivery-workflow` 编排；具体阶段按需使用测试、缺陷、排障与发布能力。测试发现原因不明的问题，交开发调查修复，经主 agent Review 后再回归；不把测试角色变成开发角色。只执行当前任务需要的阶段，不自动补齐整条流程。
- 后续阶段复用已有复现、证据和测试结果；仅在代码、配置、环境或验证范围变化时执行必要复查。
- 调用 skill 不扩大授权。只读检查不变成修复，记录 bug 不变成发送外部消息，测试通过不变成提交，发布本地不变成发布生产。
- 技能默认的自动提交、推送、合并或部署步骤不得绕过用户要求。已有明确授权不重复索取；尚需确认时先完成可审阅的准备，再说明具体待执行动作。

## 实现计划必须核对当前代码

- 编写、评审或交付实现计划时，逐项读取当前代码、相关调用方、实际表结构或 DDL、配置，注明来源及尚未核验的环境，不能仅依据旧设计、对话摘要或方法名判断功能缺失。记录核对的分支/提交及相关未提交改动；开发开始前若基线变化，重新检查受影响项。新项目明确尚无现有实现，写清技术、模块、数据、接口和运行约束，不虚构代码证据。
- 每个实施项必须写明：需求目标、当前行为及文件/类/方法证据、复用/修改/新增分类、具体差异、调用方与兼容影响、对应测试。新增项注明检索范围及现有实现为何不能满足，不能以一次关键词未命中证明不存在。
- 检查端到端调用链和全局校验，不能把单步骤行为当成整个流程行为。公共查询、校验、复制、状态推进等已有能力优先复用；不得另建重复接口或状态机，或为局部需求改变公共方法语义而不核对其他调用方。
- 计划与代码冲突时按已确认需求判断：需求要求改变旧行为则明确修改点和回归；代码已满足则标记复用/仅补测试；业务口径不明则列为待决策。不要自动把旧文档或当前代码都视为正确。
- 逐项核对未完成、关键冲突未解决时，不得宣称“可直接交付开发”。核对记录放在现有实施计划中，不另造一套重复计划。

## 测试与文档

- 单元测试不得依赖外部服务，所有外部服务必须 Mock。数据库集成测试与单元测试分开，使用隔离环境；MySQL 集成测试使用 Testcontainers。
- 测试用例文件只记录可重复执行的用例，不混入测试指令或执行结果；命令放运行说明，结果放独立报告。
- 同一需求的测试用例汇总到一个权威用例文件，包括新增场景与人工步骤；已有系统用例以“原文件路径＋用例编号”引用复用，不把全系统用例或自动化测试源码合并成一个文件。合并时保留编号映射并更新入口链接，避免多个文件维护同一预期。
- 交付测试前检索系统级、相关模块和自动化测试，逐项标记复用、修改、新增或废弃，检查前置条件、操作和预期是否重复或冲突。重复用例复用；合法的不同层级覆盖保留；旧预期与已确认需求冲突时同步修订原用例，保留追溯关系，不能只在新文件写相反预期。
- 从调用方、共享服务、数据契约和状态流转推导受影响功能，形成必须执行的回归清单，明确用例路径/编号、选择原因和执行负责人。不能只覆盖新增功能或新建测试类。
- 实现后的验收必须实际执行新增/修改用例及受影响旧用例，并逐项提供环境、版本、执行人、结果和证据。主 agent 交接清单并核验独立测试 agent 返回的结果；任务已分配、测试类存在、链接检查通过都不代表测试已执行。不得用旧版本报告证明新版本通过。
- 仅编写方案或测试设计时交付执行清单并标记未执行，不越权运行测试；实施验收阶段未执行或阻塞的必跑项不得计为通过或宣称全部验收完成。
- 根据实际变化选择测试层级和场景；业务数据需核对页面、接口、持久化与关联汇总，不能仅验证请求成功。
- 保持实现、API、设计、部署、缺陷记录和测试文档的一致性，更新本次变化影响的内容。

## MySQL 设计

- 表名、字段命名单数。每张表主键统一为 `id BIGINT AUTO_INCREMENT`，声明 PRIMARY KEY。
- 时间字段统一 DATETIME，禁止 TIMESTAMP 类型；允许 `DEFAULT CURRENT_TIMESTAMP`。有更新语义的表包含 created_at、updated_at；纯追加日志只需 created_at。
- 状态、角色及有限取值的标识字段使用 TINYINT，COMMENT 写明数字含义，映射由代码维护；禁止原生 ENUM。状态字段命名 status。
- 不建 FOREIGN KEY，关系由应用保证；关联查询字段建立索引。关联字段命名 `{表名单数}_id`。
- 涉及站点隔离的业务表包含 `site_id INT NOT NULL`，查询条件和联合索引以 site_id 为前缀；全局表不带 site_id。站点映射用代码枚举，不建 sites 配置表。
- 主表只存高频核心字段，列表不需要的扩展信息拆附属表，按需 JOIN。
- 列表统计维护冗余计数，不在列表查询中通过 COUNT(*) 关联子表实时统计；写入、删除同步维护或异步保证最终一致性。
- 唯一约束用 UNIQUE KEY；多对多反向查询字段单独建索引。
- 对象存储文件 key 字段以 `_path` 结尾，VARCHAR(500)；计数以 `_count` 结尾，INT NOT NULL DEFAULT 0。业务时间采用 processed_at、verified_at 等语义名称。
- DDL 不指定 ENGINE、CHARSET、COLLATE，由数据库统一决定。

## 容器、Java 与数据库时间

- 默认 Asia/Hong_Kong，可由运行环境覆盖。Compose 所有默认启动的业务容器显式声明 `TZ: ${TZ:-Asia/Hong_Kong}`，可用 YAML anchor 复用。
- Java 启动参数包含 `-Duser.timezone=${TZ:-Asia/Hong_Kong}`；禁止不可覆盖的固定时区。
- 业务容器不挂载宿主机 /etc/localtime、/etc/timezone；镜像需识别 IANA 时区，Alpine 保留 tzdata。Dockerfile 默认 TZ 必须可被运行环境覆盖。
- DATETIME + LocalDateTime 服务统一容器、JVM、JDBC 与连接池 session 时区；连接参数使用 `serverTimezone=${MYSQL_SERVER_TIMEZONE:${TZ:Asia/Hong_Kong}}&forceConnectionTimeZoneToSession=true`。MYSQL_SERVER_TIMEZONE 必须符合数据库实际策略。
- 检查 `SELECT @@global.time_zone, @@session.time_zone, NOW(), UTC_TIMESTAMP();`。发布验收必须检查应用实际连接池 session；人工连接或 global 设置不能替代。外部 SPRING_DATASOURCE_URL 覆盖也必须保留上述参数。
- Java 本地时间与数据库 NOW()/CURRENT_TIMESTAMP 使用相同基准，同一套 DATETIME 数据不混用 UTC 和区域时间。人工 SQL、迁移和批处理依赖当前时间时显式设置业务 session 时区。
- Testcontainers 覆盖“数据库默认 UTC、应用区域时区”，验证 Java 与数据库自动生成时间一致。
- 改连接时区不修复历史数据。历史修复须先备份，按字段来源和影响范围核验，在事务内执行并检查影响行数，禁止全库统一加减时差。
- 宿主机启用 chrony、systemd-timesyncd、ntpd 或云时间同步；容器不运行校时服务，不为校时授予 privileged/CAP_SYS_TIME。节点偏差建议小于 100ms，至少不超过 1s。
- 节点可用 timedatectl、chronyc 核验；容器用 date 和 TZ 核验。时区配置正确不等于系统时钟同步正确。
